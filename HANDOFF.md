# HANDOFF — обмін між інструментами

Над цим репозиторієм працюють **два** інструменти.

| Скорочення | Що це | Що вміє |
|---|---|---|
| **ЧАТ** | claude.ai, проєкт STARPaw | читає і пише в репозиторій, створює issues, веде правила |
| **КОД** | claude.ai/code | читає і пише, робить усю роботу по сайту: код, стилі, дизайн |

**Claude Design у процесі не використовується.** Ні канвасу, ні Import,
ні експорту бандлів, ні кнопки хендофу. Візуальні рішення приймаються
текстом у `DESIGN.md` і реалізуються КОДом. Якщо в старих текстах,
issues чи коментарях трапляється згадка про ДИЗАЙН — вона застаріла.

**КОД — єдиний імплементатор.** Усе, що потрапляє на сайт, потрапляє туди
через нього.

## Хто що бачить

| Джерело | ЧАТ | КОД |
|---|---|---|
| **GitHub Issues** | так | так |
| `CLAUDE.md` | так | так, автоматично |
| `DESIGN.md` | так | так, читає на початку сесії |
| `HANDOFF.md` | так | за вказівкою |

Архіву в репозиторії немає. Перша версія була технічним завданням, вона
відпрацювала і видалена — не посилатись на неї і не шукати `archive/`.

# Два напрямки

## 1. ЧАТ → КОД — через issue

ЧАТ створює issue з описом задачі. В issue кладеться все: і що робити,
і як це має виглядати. Окремого каналу для дизайну немає.

Людина відкриває claude.ai/code, обирає репозиторій STARPawdotnet і пише:

> Do issue #НОМЕР

КОД робить, відкриває pull request із `Closes #НОМЕР`, сам його мержить
і сам вирішує конфлікти на користь нового коду. Issue закривається саме.
Копіпасту немає.

## 2. КОД → ЧАТ — через той самий issue

Якщо КОД знайшов суперечність між джерелами — пише коментар до issue.
Але **не зупиняється на «перевірте, будь ласка»**: якщо рішення можна
ухвалити самому, він його ухвалює, робить і фіксує вибір у коментарі.
Зупинка допустима тільки тоді, коли без відповіді людини робота фізично
неможлива.

Людина в ЧАТі пише: `перевір issue НОМЕР`. ЧАТ читає коментарі, файли
й PR напряму і відповідає там само.

# Дизайн без Claude Design

`DESIGN.md` — затверджена дизайн-система. Вона вже існує (напрямок
«Вітраж клану»: вітраж і манускрипт, темне тло, кіновар / смарагд /
золото / аметист по розділах).

- **Змінити дизайн** = створити issue з описом зміни. КОД править
  `DESIGN.md` і CSS в одному PR, щоб файл і код не розходились.
- **Подивитись, що вийшло** = відкрити посилання попереднього перегляду
  з pull request або сам сайт після мержу.
- Ніяких макетів, канвасів і zip-бандлів. Джерело правди по вигляду —
  `DESIGN.md` плюс `css/`.

# Загальні правила

1. Ніщо не їде саме собою. Перехід між ЧАТом і КОДом запускає людина
   одним рядком.
2. Новий чат нічого не пам'ятає. Увесь контекст живе в репозиторії
   й в issues.
3. Задача формулюється так, щоб її зрозумів той, хто бачить проєкт
   уперше. Без «як ми домовлялись».
4. Одне issue — одна задача — один PR.
5. Ніякої збірки, npm, залежностей і фреймворків. Виняток —
   `wrangler.jsonc` і `npx wrangler deploy`, це деплой Cloudflare,
   який виконується на їхніх серверах.
6. Не вгадувати там, де є джерело. Але й не зупинятись там, де рішення
   можна ухвалити самому.
7. Усе тільки в браузері. Ніякого термінала, локальної машини
   й десктопних застосунків.
